Every merchant has separate keys for **test** and **live** mode. The key prefix decides the mode; a test key can never read or write live data.

| Prefix         | Kind                   | Where to use it    |
| -------------- | ---------------------- | ------------------ |
| `tdr_test_`    | Secret, test mode      | Your server only   |
| `tdr_live_`    | Secret, live mode      | Your server only   |
| `tdr_pk_test_` | Publishable, test mode | Browser / checkout |
| `tdr_pk_live_` | Publishable, live mode | Browser / checkout |

Send the key as `Authorization: Bearer <key>`. Keys carry scopes (for example `sessions:write`); a request outside the key's scopes gets `403 FORBIDDEN`. Publishable keys reach only the endpoints meant for the browser.

Create secret keys in **Dashboard → API keys**. Select the store and test/live mode, give the key a name, and choose its permissions. Owners and admins can manage keys; creating or revoking a key requires a recent passkey confirmation. Copy the new secret immediately: it is shown once and disappears when you dismiss it, leave the page, or change store/mode.

Keys are stored as SHA-256 hashes. The list shows only the prefix, permissions, creation date, last use and revocation status. Revoking a key stops subsequent API authentication. Connected-site keys are managed through **Connected sites**, where disconnecting also disables the site's webhooks.

Never put secret keys in `NEXT_PUBLIC_*` variables or browser bundles. The hosted checkout and `tendr.js` use a checkout session's client secret; they do not need your server's API key.

The management endpoints use dashboard cookies, store/mode headers and CSRF protection:

- `GET /v1/api_keys` returns `{ api_keys: [...] }` for the selected store and mode.
- `POST /v1/api_keys` accepts `{ name, scopes }` and returns `{ api_key, secret }` once.
- `DELETE /v1/api_keys/:id` revokes a manually issued key and returns `{ api_key }`. Repeating a revocation is safe.

Creation does not accept `Idempotency-Key`: raw secrets must never enter the response replay cache. If the creation response is lost, refresh the list, revoke the newly created key and create a replacement. Creating a live key does not bypass the platform's live-mode or wallet-readiness checks.

## Request signing (optional)

A secret key can have a signing secret. When it does, requests may carry a `Tendr-Signature` header, and a key marked "signing required" rejects any request without a valid one (`401 SIGNATURE_INVALID`).

```text
Tendr-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(signing secret, "<t>.<raw body>")>
```

- The MAC covers the exact raw body bytes sent, not re-serialised JSON. A request without a body signs `"<t>."`.
- `t` must be within 5 minutes of the server's clock.
- Several `v1=` values may be sent (one per secret) while rotating; any one matching is accepted.

```ts
import { createHmac } from 'node:crypto';

const t = Math.floor(Date.now() / 1000);
const v1 = createHmac('sha256', signingSecret).update(`${t}.${rawBody}`).digest('hex');
headers['Tendr-Signature'] = `t=${t},v1=${v1}`;
```
