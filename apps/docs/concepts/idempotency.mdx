---
title: 'Idempotency'
description: 'Retry supported mutations without accidentally creating another operation.'
---

Send `Idempotency-Key` on supported POST requests, including session creation, payment-link creation and refund requests. Use a fresh value for each logical operation and keep it with your order.

| Rule                        | Behavior                                                        |
| --------------------------- | --------------------------------------------------------------- |
| Namespace                   | Merchant, mode and authenticated credential/principal           |
| Format                      | 1–255 characters; a UUID or persisted operation reference works |
| Same key and request        | Original status/body replayed with `Idempotent-Replayed: true`  |
| Different request, same key | `409 IDEMPOTENCY_CONFLICT`                                      |
| Request still running       | `409 IDEMPOTENCY_IN_PROGRESS`                                   |
| Server error                | 5xx response is not stored                                      |
| Abandoned request           | Same request may take over after 60 seconds                     |
| Retention                   | 24 hours                                                        |

“Same request” means the same method, path/query and raw body bytes. Changing JSON serialization or whitespace can change the request hash. Switching credentials does not share the old replay entry.

## Exceptions

Not every endpoint participates. One-time API-key creation explicitly excludes replay caching so raw secrets are not persisted there. AI insight explanations also disable this layer. AI theme generation requires an idempotency key because it creates a draft.

PATCH and DELETE are not covered by the POST replay layer. Check the endpoint's own semantics.

Do not generate a new key inside every network retry. Conversely, do not reuse a key for a changed price, another order or a different refund.
