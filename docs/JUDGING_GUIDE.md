# Tendr: reviewer guide

This guide connects product claims to observable behavior, code and tests. This guide is maintained on `main`; it evaluates application baseline `deploy@2623e8d`, not the older application code on `main`. Implementation/test links are pinned to that revision. The public SDK is independently versioned at `usetendr-sdk-v0.2.0`. The [README](../README.md) is the product overview; [DEVELOPMENT.md](DEVELOPMENT.md) contains reproducible commands.

## A short review path

| Action                                                                                                            | Expected observation                                                                       | Evidence level                                                             |
| ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| Open the public playground and switch industries                                                                  | Different storefront/checkout styling; sample payment states                               | UI demonstration, no transfer                                              |
| Open the [WordPress demo store](https://wpdemo.usetendr.tech), add a product to the cart and continue to checkout | WooCommerce cart and checkout with the Tendr gateway                                       | Hosted plugin integration; inspect checkout mode before sending funds      |
| Read the recorded pilot's four transaction links                                                                  | Customer deposit, merchant settlement, owner-signed debit, external payout                 | Historical testnet chain evidence                                          |
| Create a hosted Test wallet and payment link; pay with faucet tokens                                              | Real wallet approval, API-driven state, verified settlement and a Test balance             | Repeatable testnet workflow, dependent on provider/faucet/RPC availability |
| Send less than a still-active Test quote requires                                                                 | Exact remaining amount, same deposit address and a deadline; no premature success          | Partial-payment behavior                                                   |
| Send refundable excess using manual deposit instructions                                                          | Successful order plus a return-address request, followed by owner-approved return handling | Separate order and refund lifecycle; the sub-$1 net policy still applies   |
| Review an itemized contractor invoice                                                                             | USD total independent of selected receiving token; payment requires owner signing          | Live-wallet feature; inspect code/tests without spending funds             |
| Ask the checkout assistant whether the order is paid                                                              | Answer reflects authoritative state and cannot change it                                   | Grounded assistance; provider credentials required outside mocks           |

Test use requires the original Test wallet passkey, Tidepool tokens and network gas. The production invoice flow is not a free testnet demonstration. The public invoice URL is business-specific (`https://invoice.usetendr.tech/<business>`); the host root is not an invoice page. No pre-funded judge account or shared wallet credential is supplied.

## Assessing the AI implementation

NEAR AI Cloud is a server-side dependency. The checkout assistant builds authorized store/session facts, asks the model for fact IDs, validates the response, refreshes facts and renders those facts. A model response cannot update the payment state machine.

Route comparison requests dry quotes and sorts valid results by quoted input USD, with explicit handling of unknown estimates and unavailable routes. It allocates no deposit address. An executable quote is requested separately after the user chooses a route. It does not use an LLM for routing.

Merchant insights use aggregate session metrics. Theme generation validates a draft which requires preview/publication. Neither feature signs transactions. The integration does not independently verify provider attestations or implement client-to-model end-to-end encryption; the project does not claim confidential payments or private inference.
